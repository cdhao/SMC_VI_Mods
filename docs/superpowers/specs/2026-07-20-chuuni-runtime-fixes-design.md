# 极东结社首轮运行时问题修复设计

## 目标

修复首轮实机测试发现的三项问题，同时保持已经确认的玩法规则不变：结社与学院的双向相邻收益、特色结社城市信仰购买魔法阵，以及第一阶段幻想战斗力加成。

## 相邻收益与描述

保留两项独立结算：极东魔术昼寝结社只要相邻至少一个学院，自身固定获得 `+3` 信仰；学院相邻结社时获得 `+2` 科技。多个学院不会让结社的固定信仰重复叠加，但每个专业区域仍按它与结社的实际相邻关系获得对应的 `+2` 主要产出。

本轮不编写自定义相邻 UI，也不删除学院的 `+2` 科技。中文描述改为明确指出收益接收方，避免将界面合计的 `3+2=5` 误读为结社获得 `+5` 信仰。静态测试需要分别约束固定信仰 Modifier 与学院相邻科技规则。

## 魔法阵生产与信仰购买

部室魔法阵继续替代神龛。建筑的 `PrereqDistrict` 使用原版 `DISTRICT_HOLY_SITE`，与文明六生产面板对特色区域的抽屉归类方式一致；拥有 `DISTRICT_CHUUNI_SOCIETY` 的城市通过区域替代关系满足这一前置条件。

魔法阵自身的 `PurchaseYield` 设为 `YIELD_FAITH`。目标城市必须先满足建筑的区域前置，即拥有完整的 `DISTRICT_CHUUNI_SOCIETY`；购买对象因此只限 `BUILDING_CLUB_MAGIC_CIRCLE`，也不要求城市预先拥有魔法阵。生产建造仍然可用；`PurchaseYield` 只决定购买货币，不把建筑设为只能购买。

不使用原版耶稣会教育的区域级信仰购买 Modifier，因为它会开放该区域内的一整类建筑，范围大于本轮要求。测试需要验证建筑的原版圣地区域前置、`PurchaseYield=YIELD_FAITH`，以及建筑仍未设置 `MustPurchase`。

## 第一阶段战斗力

新增阶段战斗数据库定义。玩家的 `CHUUNI_STAGE_1_UNLOCKED=1` 时，其军事单位获得 `+3` 战斗力。第一阶段不要求宗教；是否解锁仍由现有 Lua 阶段逻辑决定。

本轮只补第一阶段，暂不实现第二、第三阶段差值、第四阶段主动攻击、奇美拉或传送。文明六没有可用的玩家 Property Requirement，因此 Lua 在阶段达到一后调用一次 `AttachModifierByID`，并以独立玩家 Property 记录已附加状态。每次阶段复查都会为旧存档补挂缺失 Modifier，但不会重复附加，也不需要遍历单位。

阶段战斗定义放入新的 `Data/StageCombat.sql`，由 `.modinfo` 在 `Core.sql` 之后加载。测试需要验证 `MODIFIER_PLAYER_UNITS_ADJUST_COMBAT_STRENGTH`、`Amount=3`、Lua 附加调用和防重复 Property。

## 验证与部署

修复采用测试先行：先新增会因当前缺失机制而失败的数据库和文本契约，再实施最小 SQL/本地化变更。验证包括聚焦单元测试、Gathering Storm Schema 内存执行、统一 Civ6 工具测试、静态检查、部署后逐文件哈希一致性。

官方 Cooker 不需要重跑，因为本轮不修改 BLP 或其他美术资源。完成后重新部署 `ChuuniSociety`，但最终实机生产列表与战斗预览仍由用户在新存档或确认未缓存旧数据库的存档中验证。

## 非目标

- 不删除学院获得的 `+2` 科技。
- 不制作自定义相邻加成 UI。
- 不实现第二至第四阶段战斗效果。
- 不实现传送、奇美拉、隐形境界线或后续信仰购买范围。
- 不修改数值平衡。
