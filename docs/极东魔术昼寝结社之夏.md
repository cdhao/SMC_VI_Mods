# Codex 执行方案：极东魔术昼寝结社之夏 Civ6 Mod

## 一、任务目标

在仓库 `cdhao/SMC_VI_Mods` 中新增一个独立的《文明六》Mod：

```text
mods/ChuuniSociety/
```

中文暂定名称：

> 极东魔术昼寝结社之夏

首个发行里程碑 `v0.1` 只实现：

* 文明主体；
* 领袖小鸟游六花；
* 特色圣地区域；
* 替代神龛的部室魔法阵；
* 中二值及四阶段系统；
* 特殊总督奇美拉；
* 六花领袖能力；
* 不可视境界线改良；
* 魔法阵传送；
* 必要的中文本地化；
* 最小可用图标占位。

不要在 `v0.1` 实现其他四位领袖。后文的 Phase 1–9 均属于 `v0.1` 内部实施阶段，不代表需要在第一次提交中完成全部功能。

## 1.1 规则集与资料片范围

本 Mod 仅支持：

```text
Gathering Storm（风云变幻）规则集
Players:Expansion2_Players
```

原因：

* 奇美拉使用真实总督系统；
* 总督数据表、Requirement 和界面依赖资料片规则；
* 首版不维护 Rise and Fall 与 Gathering Storm 两套 FrontEnd 配置和测试矩阵。

`ChuuniSociety.modinfo` 只声明 Gathering Storm 依赖：

```xml
<Dependencies>
  <Mod id="4873eb62-8ccc-4574-b784-dda455e74e68" title="Expansion: Gathering Storm" />
</Dependencies>
```

不要额外强制依赖 Rise and Fall。文明选择界面的 `Players` 和 `PlayerItems` 统一使用 `Players:Expansion2_Players`。

首轮开发先保证所有机制可运行、UI与实际结算一致，再根据实际游戏数据统一调整平衡数值；不要在技术验证阶段反复改数值。

# 五、中二值实现方案

## 5.1 推荐实现

将中二值定义为一个：

* 不在地图生成；
* 可以累积；
* 库存上限固定100；
* 不会消费；

的自定义战略资源。

SQL参考：

```sql
INSERT INTO Types (Type, Kind)
VALUES ('RESOURCE_CHUUNI_VALUE', 'KIND_RESOURCE');

INSERT INTO Resources
    (ResourceType, Name, ResourceClassType, Frequency, RevealedEra)
VALUES
    ('RESOURCE_CHUUNI_VALUE',
     'LOC_RESOURCE_CHUUNI_VALUE_NAME',
     'RESOURCECLASS_STRATEGIC',
     0,
     0);

INSERT INTO Resource_Consumption
    (ResourceType, Accumulate, PowerProvided,
     BaseExtractionRate, ImprovedExtractionRate, StockpileCap)
VALUES
    ('RESOURCE_CHUUNI_VALUE', 1, 0, 0, 0, 100);
```

参考 Grace 的 `RESOURCE_INFECTED_BLOOD`，但将 `StockpileCap` 改为100。

## 5.2 中二值获取

初版不要依赖复杂的资源产出 Modifier。

使用 Gameplay Lua 在玩家回合开始时计算：

```text
每座 DISTRICT_CHUUNI_SOCIETY：+1中二值/回合
每座 BUILDING_CLUB_MAGIC_CIRCLE：+1中二值/回合
```

处理流程：

```lua
OnPlayerTurnActivated
    → 判断玩家是否为本文明
    → 枚举玩家城市
    → 统计特色区域数量
    → 统计魔法阵数量
    → 本回合增加对应中二值
    → 总量限制为100
    → 检查阶段解锁
```

理由：

* 逻辑透明；
* 便于调试；
* 不依赖不确定的战略资源区域产出 Modifier；
* 可以准确限制在100；
* 后续容易调整产量；
* 可直接复用 Grace 的资源读取与修改函数。

必须防止同一回合重复执行，使用：

```text
CHUUNI_LAST_RESOURCE_TICK_TURN
```

玩家 Property 记录上次结算回合。

## 5.3 数值同步

每次中二值发生变化后调用，并在玩家回合开始时无条件复查一次：

```lua
UpdateChuuniStage(playerID)
```

阶段定义：

```text
0：未成立
中二值 >= 1：第一阶段
中二值 >= 20、已创立宗教、第一阶段已解锁：第二阶段
中二值 >= 50、已创立宗教、第二阶段已解锁：第三阶段
中二值 >= 100、已创立宗教、第三阶段已解锁：第四阶段
```

阶段严格按顺序解锁，只会上升，不会下降。第一阶段不要求宗教，第二、第三、第四阶段都要求玩家已经创立宗教；未创立宗教的玩家不能从第一阶段越过第二阶段直接进入第三或第四阶段。

玩家创立宗教时必须主动调用 `UpdateChuuniStage(playerID)`。如果没有可靠的宗教创立事件，则由每回合开始时的无条件复查保证宗教门槛解除后可以继续升级，即使中二值已经达到100且不再变化。

# 六、阶段系统

## 6.1 阶段最终值

阶段效果为替换，不是累加。

```text
第一阶段：幻想战斗最终为+3
第二阶段：幻想战斗最终为+5
第三阶段：幻想战斗最终为+8
第四阶段：幻想战斗维持+8
```

## 6.2 推荐技术结构

Lua只负责设置阶段 Property：

```lua
player:SetProperty("CHUUNI_STAGE", stage)
```

SQL/XML Modifier负责实际效果。

不要用Lua逐回合遍历所有单位并修改战斗力。

建立四套 Requirement：

```text
REQUIREMENT_CHUUNI_STAGE_AT_LEAST_1
REQUIREMENT_CHUUNI_STAGE_AT_LEAST_2
REQUIREMENT_CHUUNI_STAGE_AT_LEAST_3
REQUIREMENT_CHUUNI_STAGE_AT_LEAST_4
```

使用玩家 Property Requirement。

第二、第三、第四阶段的 RequirementSet 还必须包含“玩家已创立宗教”条件。阶段解锁逻辑同时检查前一阶段的 unlocked Property，保证阶段只能依次推进。

为避免阶段效果叠加，推荐采用差值：

```text
阶段1：+3
阶段2：额外+2
阶段3：额外+3
阶段4：不追加基础战斗力
```

最终结果：

```text
阶段1：3
阶段2：3+2=5
阶段3：3+2+3=8
阶段4：8
```

对军事单位和宗教单位分别创建 Modifier：

```text
军事单位：ADJUST_COMBAT_STRENGTH
宗教单位：ADJUST_RELIGIOUS_STRENGTH
```

具体 ModifierType 从原版数据库或现有 Mod 中搜索确认，不要凭空猜测名称后直接提交。

# 七、特色区域：极东魔术昼寝结社

## 7.1 区域定义

```text
DISTRICT_CHUUNI_SOCIETY
```

替代：

```text
DISTRICT_HOLY_SITE
```

采用 `SELECT ... FROM Districts WHERE DistrictType='DISTRICT_HOLY_SITE'` 复制基础字段，参考 Grace 的方舟区域实现。

保留：

* 圣地正常功能；
* 允许创立圣城；
* 圣地相关宗教建筑；
* 大预言家点数；
* 圣地贸易路线效果；
* 圣地专家产出。

## 7.2 大预言家点数

每座特色区域：

```text
+2大预言家点数/回合
```

这是最终值，不是在圣地原有的1点基础上额外增加2点。复制圣地区域数据后，应覆盖对应记录，使特色区域最终每回合提供2点大预言家点数。

通过：

```text
District_GreatPersonPoints
```

实现。

## 7.3 与学院相邻

规则：

```text
只要至少相邻一个学院，特色区域获得固定+3信仰。
相邻多个学院不重复。
```

普通 `Adjacency_YieldChanges` 通常会按每个相邻学院重复结算，不能直接表达“不重复”。

实现优先级：

### 方案A：Requirement Modifier

给区域挂一个条件 Modifier：

```text
区域相邻至少一个 DISTRICT_CAMPUS
→ 区域+3信仰
```

优先搜索原版是否存在“区域相邻指定区域”的 Requirement。

### 方案B：Lua城市扫描

若没有可靠 Requirement：

* 城市完成区域时；
* 玩家回合开始时；

扫描特色区域周围六格是否存在学院。

存在时给城市设置：

```text
CHUUNI_CITY_HAS_CAMPUS_ADJACENCY = 1
```

再由 Modifier提供+3信仰。

### 方案C：暂时改为每个学院+3

仅作为技术原型，不作为最终版本。

## 7.4 对外提供标准相邻

目标：

```text
相邻专业化区域获得+2对应相邻产出。
```

推荐使用动态SQL生成：

```text
学院：+2科技
剧院广场：+2文化
商业中心：+2金币
港口：+2金币
工业区：+2生产
圣地：+2信仰
军营：根据是否存在合理的主产出决定是否排除
```

不要尝试对所有区域使用一个通用“标准相邻”字段。

显式维护允许列表：

```text
DISTRICT_CAMPUS
DISTRICT_THEATER
DISTRICT_COMMERCIAL_HUB
DISTRICT_HARBOR
DISTRICT_INDUSTRIAL_ZONE
DISTRICT_HOLY_SITE
```

特色替代区域也需要测试是否继承原区域相邻规则。

# 十、单位升级折扣

## 10.1 优先使用原版 Modifier

先查询原版政策卡“职业军队”等对应定义：

```text
单位升级金币折扣
单位升级战略资源折扣
```

不要使用Lua模拟扣费，除非原版 Modifier 无法按城市领土条件生效。

重点检索数据库：

```text
PolicyModifiers
Modifiers
ModifierArguments
RequirementSets
RequirementSetRequirements
Requirements
RequirementArguments
```

参考方向：

```text
POLICY_PROFESSIONAL_ARMY
POLICY_FORCE_MODERNIZATION
```

具体政策名称和 ModifierId 以本地数据库为准。

## 10.2 城市条件

需要判断：

```text
单位当前所在城市是否拥有 BUILDING_CLUB_MAGIC_CIRCLE
```

如果原版 Modifier不支持按单位所在地城市建筑判断，则分两步：

1. Lua在单位选择、移动完成或升级前同步单位 Property；
2. Modifier检查单位 Property后应用折扣。

不要直接在 `Events.UnitUpgraded` 后退款，除非找不到任何升级费用 Modifier。

### 退款方案仅作降级路径

如果必须使用Lua：

* 监听 `Events.UnitUpgraded`；
* 升级前费用难以准确保存；
* 需要从升级单位类型和原单位类型反算费用；
* 容易和政策卡叠加出错。

因此退款实现优先级最低。

# 十一、魔法阵传送

## 11.1 第一版目标

单位必须：

```text
站在拥有部室魔法阵的 DISTRICT_CHUUNI_SOCIETY 地块上
```

目标必须：

```text
属于同一玩家
目标城市拥有部室魔法阵
目标特色区域地块可容纳该单位
```

传送后：

```text
耗尽全部移动力
本回合不能再次传送
```

允许传送的单位必须位于地图上且属于 `DOMAIN_LAND`，具体包括：

```text
陆地战斗单位
陆地平民单位，包括建造者、开拓者和宗教单位
伟人单位
```

明确排除：

```text
海军单位
空军单位
商人
间谍
不在地图上以普通单位状态存在的特殊单位
```

## 11.2 推荐实现顺序

### 技术原型

先不要实现自定义目标选择UI。

先实现一个调试函数：

```lua
TeleportUnitToFirstValidMagicCircle(playerID, unitID)
```

验证：

* 单位移动；
* 单位类型兼容；
* 目标占用判断；
* 移动力清零；
* 陆地战斗单位、平民单位、宗教单位和伟人是否正常；
* 海军、空军、商人和间谍是否被拒绝；
* AI单位不会导致报错。

### 正式实现

需要一个 Unit Action 或 UI按钮：

```text
传送至部室魔法阵
```

点击后进入目标选择模式，只高亮合法魔法阵。

可能需要：

```text
ContextPtr
LuaEvents
UILens
UnitManager
WorldInput
```

这部分与 Grace Mod 现有代码没有直接参考，应单独作为技术任务。

### 降级方案

若自定义地图选点UI开发量过高：

* 点击传送按钮；
* 弹出城市列表；
* 选择目标城市；
* 执行传送。

城市列表虽然不如地图选点自然，但更容易稳定实现。

# 十二、特殊总督奇美拉

奇美拉建立在 Gathering Storm 规则集提供的真实总督系统上。本 Mod 不提供无资料片或标准规则集下的兼容实现。

## 12.1 技术风险

这是整个方案中风险最高的部分之一。

目标：

```text
免费招募
不消耗总督头衔
不使用普通晋升点
随中二值阶段自动解锁能力
建立与调任1回合
```

## 12.2 推荐先做技术验证

创建最小测试：

1. 定义一个自定义 Governor；
2. 确认可以正常出现在总督界面；
3. 确认可以免费授予玩家；
4. 确认可以设置建立时间；
5. 确认Lua是否能自动授予 GovernorPromotion；
6. 确认晋升是否会错误消耗总督点。

## 12.3 推荐实现

### 方案A：真实总督＋自动晋升

XML定义：

```text
GOVERNOR_CHIMERA
四个专属 GovernorPromotion
晋升树
Modifier
```

Lua达到阶段后自动授予对应晋升。

优点：

* UI完整；
* 玩家能看到成长；
* 与总督系统一致。

风险：

* Lua自动授予晋升API可能有限；
* 免费招募和不消耗头衔需要测试。

### 方案B：真实总督＋阶段Property

只定义一个基础奇美拉总督。

阶段效果不通过 GovernorPromotion授予，而是通过：

```text
玩家阶段Property
+
城市由奇美拉督管Requirement
```

自动生效。

优点：

* 不需要动态晋升API；
* 不消费总督点；
* 效果易控制。

缺点：

* 总督界面不一定显示四阶段能力已经解锁。

第一版优先采用方案B。

可以在奇美拉说明文本中完整列出四阶段能力。

# 十三、奇美拉城市产出

奇美拉城市获得：

```text
第一阶段：floor(中二值×10%) 信仰
第二阶段：再获得 floor(中二值×10%) 文化
第三阶段：再获得 floor(中二值×10%) 科技
```

这些产出必须显示在奇美拉督管城市的城市产出面板中，因此正式实现优先使用城市 Yield Modifier，不直接用Lua增加玩家科技、文化或信仰库存。

推荐将：

```text
floor(当前中二值×0.10)
```

拆成10档增量 Modifier。中二值达到10、20、30……100时，每档为对应产出额外增加1。Lua只负责同步中二值产出档位 Property，Modifier负责把产出挂到奇美拉督管城市，从而使城市面板、回合收益和实际结算保持一致。

流程：

```lua
currentValue = GetChuuniValue(playerID)
yieldStep = math.floor(currentValue * 0.10)
player:SetProperty("CHUUNI_CHIMERA_YIELD_STEP", yieldStep)
```

注意区别：

* 第一阶段只在奇美拉城市显示并结算信仰；
* 第二阶段再显示并结算文化；
* 第三阶段再显示并结算科技；
* 调任后旧城市的面板产出必须移除，新城市必须获得正确档位；
* 中二值变化后，城市面板最迟在下一次游戏刷新或回合结算前同步。

只有在确认原版 Modifier 无法同时满足动态档位和督管城市条件时，才允许将Lua直接发放作为降级方案；采用降级方案前必须记录技术验证结果，并重新让用户确认，因为它不满足城市面板显示要求。
